# Adopt the Quiet Reading Room design language (DESIGN.md as canonical spec)

Status: accepted — extends ADR-0002 (shadcn vocabulary) and ADR-0003 (tiered tokens), which remain in force. Foundation migration tracked under [PRD #32](https://github.com/davidinoa/rss-feed-v0/issues/32). Revisit if the visual direction shifts away from a reading-first editorial register, or if Stitch (the tool) changes its DESIGN.md format meaningfully.

We commit to a named visual language — "Quiet Reading Room" — and treat `DESIGN.md` at the repo root as its canonical spec. The current visual scaffolding (GitHub-style neutrals, single blue accent, Inter throughout) was inherited from ADR-0002 as a placeholder, never a committed direction; meanwhile the product's purpose (sustained reading of feed content) calls for a warmer, more editorial register than a developer-dashboard palette delivers. Quiet Reading Room anchors on a warm parchment canvas (`#FAF7F2`), a single muted Burnt Amber accent (`#A85426`) used for unread indicators / primary CTAs / focus rings / links, Source Serif 4 for display headings paired with Inter for UI, and hairline borders preferred over shadows. `DESIGN.md` captures the spec in the open Stitch DESIGN.md format — five canonical sections (Atmosphere, Palette, Typography, Components, Layout) plus a sixth Agent Prompt Guide that surfaces phrases-to-use and migration guidance for AI tooling reading the document. We use the Stitch format because it is the established open standard for agent-readable design specs, not because we use Stitch the tool itself.

Scope of this ADR is foundation only: migrating primitive + semantic palette values, adding Source Serif 4 + a 14-step typography utility scale, adding a spacing scale and depth scale, and refining the **existing** Button component to the spec. The two-tier token architecture from ADR-0003 survives unchanged — only the values change. The shadcn-compatible semantic vocabulary from ADR-0002 survives unchanged — `--background`, `--primary`, `--card`, etc. keep their names so future `npx shadcn add` calls continue to drop in without translation. New components described in DESIGN.md §4 (Card, Feed Item, Reading View, Sidebar, Empty State, Toast, Pill / Tag) are explicitly **out of scope** for this ADR — they describe future product surfaces not yet built. DESIGN.md §4 carries a scope callout and §6 carries an in-scope / out-of-scope breakdown so any agent reading the document cold knows which sections describe live work versus aspirational specs; six issues that would have built those surfaces were closed as premature against [PRD #32](https://github.com/davidinoa/rss-feed-v0/issues/32) to keep the boundary honest.

Documentation responsibility splits cleanly: `DESIGN.md` (repo root) is the **visual spec** — palette values, type scale, component design intent — read by anyone (human or agent) asking "what should this look like." `docs/design-system.md` is the **engineering reference** — file naming, shadcn install conventions, Storybook story patterns, dark-mode rules, axe a11y test setup — read by anyone writing component code. The previous overlap (design-system.md duplicating token values) is removed as part of this slice; DESIGN.md + the Storybook tokens catalog become the single source of truth for visual values, while design-system.md narrows to engineering practice.

## Documented ambiguities

- **Asymmetric dark-mode `--primary` remap.** Burnt Amber (`#A85426`) fails WCAG AA contrast against the dark-mode canvas Midnight Slate (`#15130F`) at 3.5:1; the semantic `--primary` token therefore remaps to Amber Glow (`#D67E45`, 6.12:1) in dark mode rather than to a dark-counterpart of the same hue. This is the only semantic token where the dark-mode partner is a different primitive value rather than a same-role darker version. It bends the "unified palette, dark is a remap" invariant from ADR-0003 in this one spot — preserved deliberately because accessibility wins over architectural neatness. If a second token ever needs the same treatment, consider promoting "accent variants" to a documented pattern rather than treating each as a one-off. (Note: the canonical Burnt Amber hex was tuned during slice #34 from the original DESIGN.md draft value `#B8612D` to `#A85426` so the light-mode primary CTA pair would also pass WCAG AA against `--warm-parchment` at 4.96:1.)
- **Aspirational vs live boundary in DESIGN.md.** DESIGN.md §4 describes seven components that do not exist in the codebase (Card, Feed Item, Sidebar, Reading View, Empty State, Toast, Pill / Tag). The document's top-level Status note, §4 scope callout, and §6 in-scope / out-of-scope breakdown make this explicit. The risk is that an agent reads §4 and starts building; the mitigation is the cross-reference to [PRD #32](https://github.com/davidinoa/rss-feed-v0/issues/32), which lists six closed issues that would have built those components. Future PRDs that revive any of those surfaces should reference DESIGN.md as the spec — the design intent does not need to be re-derived.
- **Stitch DESIGN.md format despite no Stitch tooling.** We adopt the open Stitch format for agent readability — there is no Stitch project, no Stitch CLI integration, no MCP server. The format is treated as documentation convention, not as tooling input. The "Project ID" header field from the canonical Stitch template is dropped because we would otherwise be putting a placeholder where Stitch expects a real ID; the title-only header is the only deviation from the published format.
- **Reading-first language for a not-yet-reading-shaped product.** DESIGN.md's atmosphere prose talks about reading lamps, gallery-curated articles, and pull quotes — language that fits a product with a built reading surface. The current app has a timeline route and a feeds route but no reading view. The atmosphere language is aspirational; agents picking up foundation work should not feel compelled to instantiate that language via UI choices outside scope (e.g., adding hero illustrations to the landing page just because DESIGN.md's voice is editorial). Foundation slices touch tokens, the typography scale, layout scales, and the existing Button — nothing else.
