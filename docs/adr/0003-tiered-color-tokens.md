# Tiered color tokens (primitive + semantic) on top of shadcn vocabulary

Status: accepted — supersedes the single-tier color setup introduced in ADR-0002. Revisit if a second platform (iOS/Android) or designer-driven Figma token sync becomes a real workflow, or if shadcn changes its semantic vocabulary in a major release.

We split the color tokens added by ADR-0002 into two tiers: **primitives** (raw palette, named by appearance — e.g. `--neutral-100`, `--blue-600`) and **semantics** (intent-bearing aliases named by role — `--background`, `--primary`, `--destructive`, kept identical to shadcn's vocabulary). Semantics reference primitives via `var(...)` and never inline hexes. The flat single-tier setup was rejected because the brand palette was invisible in code and identical hex values were silently duplicated across roles (`#2563EB` appears three times in `:root` for primary/ring/unread-indicator with nothing forcing them to stay equal when the brand blue shifts); a third "component" tier (e.g. `--button-bg`) was rejected as premature with one styled component in the codebase. Both modes share one unified palette rather than parallel light/dark palettes — the `.dark` block becomes a remap ("`--background` is `--neutral-0` in light, `--neutral-1000` in dark") rather than a duplicate hex set, which keeps the system coherent and future additional themes (high contrast, etc.) become palette swaps rather than copy-paste blocks.

Primitives are kept private: they live on `:root` as raw CSS variables but are NOT exposed through `@theme inline`, so `bg-neutral-100` does not exist as a Tailwind utility and consumers must reach for the semantic alias (`bg-muted`, `bg-card`, etc.) instead. To make this enforceable we also disable Tailwind v4's built-in color palette with `@theme { --color-*: initial; }`, removing the `bg-blue-600`-style escape hatch that would otherwise let consumers bypass the semantic layer and break theming the moment the brand blue shifts. The trade is real — devs lose Tailwind's default palette as a prototyping convenience — but the upside (every `bg-*` in the codebase is self-documenting about design intent, and a palette swap touches one file) is worth it for a solo-dev project where there are no team-habit costs.

Scope is narrow: color and radius are formalized as tokens; typography beyond `--font-sans` / `--font-serif`, spacing, motion, elevation, and z-index are NOT tokenized — Tailwind defaults cover them and no current consumer demands a custom value. State variants (hover, active, focus) remain implicit via Tailwind's opacity modifier (`hover:bg-primary/90`) inherited from shadcn — explicit `--primary-hover` tokens were rejected because they'd force CVA-patching on every `npx shadcn add`, re-introducing the drift problem ADR-0002 was written to prevent. The CSS file is the single source of truth; W3C Design Tokens / Style Dictionary / Terrazzo were rejected because we have no second platform, no Figma sync, and no designer handoff that would earn the build-tooling cost. Storybook docs derive their values at runtime via `getComputedStyle()` reading from the DOM, so the catalog never drifts from the CSS.

## Documented ambiguities

- **Off-scale primitive step numbers.** Three neutrals land on non-standard scale points (`--neutral-150`, `--neutral-850`, `--neutral-925`) because the GitHub-style palette doesn't fit Tailwind's 50/100/200/… grid cleanly. We chose honesty (preserve actual brand values, accept odd numbers) over naming neatness (round to standard steps, slightly shift values). The odd numbers ARE the documentation: they signal "this is a curated palette, not an algorithmic scale."
- **Single-use primitive `--blue-950: #1A2332`.** Referenced by exactly one semantic (`--accent-subtle` in dark mode). Promoted to primitive anyway because allowing inline hexes in the semantic layer would leak the abstraction and future contributors (human or agent) would copy the pattern. The cost is one underused primitive name; the benefit is a hard rule — semantics always reference primitives.
- **Implicit state expression.** Hover/active/focus colors use Tailwind's opacity modifier (`hover:bg-primary/90`) rather than named state tokens. This is intentional, not an oversight. If brand-kit specs ever diverge from a simple opacity overlay (e.g. "primary darkens to a specific hex on hover, not 90% alpha"), promote affected states to explicit tokens — don't mix the two patterns piecemeal across the codebase.
- **Near-duplicate neutrals.** `--neutral-900: #1A1D21` (light-mode foreground text) and `--neutral-925: #161B22` (dark-mode card surface) differ by ~1% luminance and could visually be collapsed. We keep both because they describe distinct brand-kit values used in distinct roles; collapsing would either drift the brand or force a role to use a value it wasn't specified with.
